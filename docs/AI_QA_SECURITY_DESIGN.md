# XunZi-PD AI evidence Q&A: safety and deployment design

**Status: design only — not enabled in the public app.**

This document defines the minimum conditions for adding an AI evidence Q&A surface to XunZi-PD. It is deliberately separate from the static GitHub Pages application. No API key, user question, or private research note is currently sent anywhere by the public site.

## Product scope

The assistant may help a reader understand **already loaded, frozen evidence** for one selected gene. Its allowed questions are limited to:

1. why the gene appears in the candidate view;
2. what the MPTP model recorded;
3. what the reported ranks mean;
4. whether the protein has recorded network context;
5. what the PFF model recorded;
6. pathway or biological-process membership;
7. whether the loaded PD genetics reference mentions the gene; and
8. what the loaded evidence does and does not establish.

It must not diagnose, triage, advise on treatment, recommend a drug, recommend a therapeutic target, establish causality, call a result replicated or biologically validated, or infer facts that are absent from the loaded evidence.

## Trust boundary

```text
visitor browser
  └─ sends: short question + selected gene ID + interface language
       └─ XunZi-PD Q&A backend
            ├─ validates allowed question scope and request size
            ├─ resolves evidence from an approved frozen source snapshot
            ├─ applies medical/research-boundary rules
            └─ calls the model with the approved evidence only
                 └─ returns: answer + field-level citations + boundary notice
```

The browser must never send its notes, shortlist, browsing history, or an API key. The backend must never accept evidence values supplied by the browser as authoritative. A visitor may select a gene identifier, but the backend independently resolves its evidence from the approved frozen snapshot.

## Answer contract

Every successful response must contain:

```json
{
  "answer": "Plain-language explanation constrained to the supplied evidence.",
  "evidence": [
    {
      "label": "MPTP expression",
      "source": "frozen primary evidence field",
      "value": "shown exactly as supplied to the model"
    }
  ],
  "boundary": "Research context only; this does not establish causality or a validated therapeutic target.",
  "status": "answered | insufficient_evidence | out_of_scope"
}
```

The citations are generated by the backend from the retrieved fields, not invented by the model. `insufficient_evidence` is required whenever a field is absent. `out_of_scope` is required for medical or treatment questions, rather than a softened answer.

## Privacy rules

- Accept at most a selected gene ID, language, and a short question; do not request name, email, health information, files, or account data.
- Do not transmit browser-only notes, shortlist entries, or progress state.
- Do not store request bodies or model answers in application logs. Operational logs may contain only a timestamp, status class, and a non-reversible rate-limit key.
- Show a clear notice before sending a question: **"Your question and the selected gene ID will be sent to the AI service. Do not include personal or health information."**
- Do not promise zero retention without a provider contract that supports it. OpenAI documents that API data controls and retention vary by endpoint and account setting; review the current policy before deployment.

## Key and backend rules

- The OpenAI API key exists only as a deployment-platform secret (for example, `OPENAI_API_KEY`), never in JavaScript, HTML, Git history, screenshots, or GitHub Actions logs.
- Use a project-scoped API key with a per-project budget and rate limits; never use an organization admin key.
- The backend calls the Responses API server-side. OpenAI's API documentation explicitly says that API keys must not be exposed in client-side code and should be loaded from an environment variable or key-management service on the server.
- Keep the allowed browser origin list explicit: `https://pc-wang-ai.github.io` during the public pilot. Reject all other origins.
- Enforce a per-IP/per-session rate limit before any model call, plus a hard daily request and spend ceiling at the provider/project level.
- Do not enable web search, file search, remote tools, browser control, or arbitrary URL retrieval for this feature. The answer context is the approved frozen evidence only.

## Evidence retrieval rules

1. Pin a source-bundle revision before deployment and record its commit/hash in the backend configuration.
2. Retrieve only fields already present in the frozen public bundle.
3. Preserve gene symbols, Ensembl IDs, study accessions, pathway names, database names, and source identifiers byte-for-byte; never translate them.
4. Attach each response field to its original evidence layer: primary/MPTP, network, PFF, pathway membership, or PD reference context.
5. Do not calculate a new score, threshold, rank, enrichment result, or biological conclusion in the backend.

## Required refusal behaviour

| Request type | Required response |
| --- | --- |
| Diagnosis, prognosis, symptoms, or treatment | State that XunZi-PD is research-only and cannot provide medical advice. |
| "Is this a validated target?" | State that the loaded analysis does not validate therapeutic targets. |
| Evidence absent from the approved snapshot | State that the loaded evidence cannot answer the question. |
| Prompt injection or instructions to ignore safeguards | Ignore the instruction and answer only within the allowed evidence scope, or refuse. |
| More than one gene / unclear gene | Ask the visitor to select one gene in the app before answering. |

## Deployment gate

The UI remains disabled until every item below is true:

- [ ] A serverless backend project exists and its production domain is known.
- [ ] `OPENAI_API_KEY` and a pinned model name are stored only in that platform's encrypted environment variables.
- [ ] Provider project budget, rate limits, and usage alerts are configured.
- [ ] CORS permits only the XunZi-PD public origin.
- [ ] The approved frozen evidence revision is pinned and retrieval tests pass.
- [ ] Automated tests cover: medical refusal, missing evidence, prompt injection, citation attachment, CORS rejection, and rate limiting.
- [ ] The public privacy notice and third-party attribution review are approved.
- [ ] A human has tested desktop and mobile flows without entering personal data.

## Recommended rollout

1. Deploy the backend to a separate serverless domain with the UI still hidden.
2. Run a private test with fixture data and no personal information.
3. Enable a small public pilot with a low request cap and visible feedback route.
4. Inspect anonymous aggregate failures and safety refusals; do not retain questions for product analytics.
5. Only then make the Q&A entry point visible on GitHub Pages.
